## 二、实验一：奖励函数定义一切 ✓ 完整复现

`completions/mean_length`（token）：**174.8 → 95（60 步内）→ 58.75（300 步）**

- 模型从"长篇大论"被奖励函数硬生生拽向"极短回答"，与文章"几步内快速收敛"一致。
- 复现要点：**学习率必须是 2e-6**。最初用 TRL 默认 1e-6 时 300 步长度几乎不动
  （118→117.6），换成作者配置后 60 步内即腰斩。GRPO 对 lr/temp 极其敏感。
- 细节：TRL 的 `mean_length` 以 token 计，奖励以字符计，两条曲线的"20"不是同一单位，
  收敛平台在 ~60 token（≈200 字符）而非 20——与文章曲线形状一致，无需纠结绝对值。

## 三、实验二：可验证奖励的组大小扫描 ✓ 结论复现（k=8 最优）

| k | 起点(first30) → 终点(last30) | 增益 | 文章结果 |
|---|------------------------------|------|---------|
| 2 | 0.328 → 0.362 | +0.034 | 0.41 → 0.58（+0.17，最差）|
| **8** | **0.304 → 0.464** | **+0.16** | **0.41 → 0.67（+0.26，最优）** |
| 16 | 0.365 → 0.407 | +0.042 | 0.39 → 0.61（+0.22）|

**核心结论复现：k=8 显著优于 k=2 和 k=16。**

- 机制（对应学习指南 §3.1/§4）：组内方差归零的组不产生梯度
  （`frac_reward_zero_std`：k=2 约 75% vs k=8 约 50-60%）；k 大→baseline 稳，
  但每步 prompt 数 = generation_batch_size/k，k=16 时每步只有 1 道题，多样性崩了。
- 与文章的差距：我们的绝对基线（~0.33）低于文章（0.41），增益也更小。
  探针诊断显示判分管线无误（chat 模板 0.50 vs 裸 prompt 0.00——chat 模板必要），
  差距主要来自模型行为的样本波动与 prompt 模板细节差异。
- k=8 曲线中途有深谷（~150 步处 0.37→0.23）后强力回升到 0.46——
  共享数据集循环 + 无 KL 约束下的正常震荡，wandb 上看全程更直观。

## 四、实验三：Reward Hacking —— 两版对照，机制清晰

被优化奖励 = 数 completion 里 Python code block 个数（不看代码对错）；
真实奖励 = MBPP assert 通过率，`reward_weights=[1, 0]` 只记录不优化。

### #5 capped 版（块数上限 1）
- hack 奖励**第 1 步即饱和在 1.0**，之后 300 步纹丝不动；
- 策略几乎冻结：真实奖励 0.338→0.458（噪声级），长度 240→226。
- **教训：奖励一旦饱和，组内方差归零，梯度随之消失**——优化器"无事可做"。

### #6 uncapped 版（块数不设上限，作者本意）
- hack 奖励 1 → ~2.0（max 2.31）：策略学会了"多塞 code block"；
- 真实奖励全程剧烈震荡：first30=0.326，**中途深跌至 0.00**，last30 回升到 0.371；
- 长度 145 → 220-350 区间膨胀（中途单步均值最高 ~350）。
- **机制**：策略向"2 块"平衡点漂移后，组内方差再次归零、梯度再度消失
  ——和 capped 版同一原理，只是饱和点从 1 挪到了 2。
  熵随训练下降、探索减少后，策略就被冻在最新平衡点上。

### 与文章的差距
文章现象更戏剧化（长度顶死 512、真实奖励持续归零）。我们的复现中 hacking
效应真实存在（被刷的指标上升、真实能力剧烈失稳），但策略在"2 块平衡点"
提前冻结。可能原因：vLLM 采样差异、温度/熵衰减路径、作者奖励函数的计数细节
（如按 ``` 标记数而非配对数）不完全可知。**方向一致，幅度温和**——
这本身就是"组相对 advantage 依赖组内方差"这一机制的又一次现场演示。

## 五、给学习者的三个连接点（对照《TRL_GRPO_源码学习指南.md》）

1. **奖励函数即目标**（§2/§5）：exp1 里长度被拽向 20；exp3 里块数被刷上去——
   `_calculate_rewards()`（L1625）返回什么，策略就优化什么，没有任何隐藏保护。
2. **组内方差 = 梯度的血液**（§3.1 `num_generations` + §4）：exp2 的 k 扫描、
   exp3 两版的"饱和即冻结"，全是 `frac_reward_zero_std` 这一个指标的不同面孔。
   源码锚点：advantage 归一化在 `_compute_loss()`（L3061）。
3. **超参敏感度**（§3.1）：lr 1e-6→2e-6 的差异决定了"完全学不动"和"快速收敛"；
   这也是为什么复现论文/文章时要对齐**全部**超参而不是只对齐框架。

## 七、消融实验：旧配置为什么纹丝不动（2026-10-01 补充）

主实验时发现 lr=1e-6/temp=1.0/cap=128 跑 300 步长度纹丝不动（119.7→117.6），
对齐作者配置后立刻正常。为归因做了 (lr × temp × cap) 立方体，补齐全部 6 个角
（各 150 步，wandb run：`ablation_temp / ablation_lr / ablation_cap / ablation_cap_v2`）：

| 角 | lr | temp | cap | 结果（mean_length 窗口均值）| 速度 |
|----|-----|------|-----|------------------------------|------|
| R_old | 1e-6 | 1.0 | 128 | 120 → 117.6（300 步）| ~0（死）|
| R_new | 2e-6 | 0.7 | 256 | 175 → 95（60 步）| 起飞 |
| temp 组 | 2e-6 | **1.0** | 256 | 149 → 90 | 快 |
| lr 组 | **1e-6** | 0.7 | 256 | 166 → 154 | 缓 |
| cap 组 | 1e-6 | 1.0 | **256** | 166 → 145 | 缓（比 R_old 快 ~20 倍）|
| cap_v2 组 | 2e-6 | 0.7 | **128** | 109 → 81（clip 0.81→0.19）| 能学但被压 |

**归因：旧配置的冻结 = cap=128（毁掉 81% 样本的 EOS 信号）× lr=1e-6（更新太弱），
两个因子相乘；单独修任何一个都能"解冻"，两个都修才起飞。温度从头到尾是次要因素。**

方法要点（每个组只和自己的参照差一个变量）：
- temp 组 / lr 组锚定 R_new（回答"新配置里这个变量重要吗"）
- cap 组锚定 R_old（回答"旧配置平线的元凶是谁"）
- cap_v2 组锚定 R_new（回答"最好配置遇上截断会不会被拖垮"——会，但强驱动能穿过去）

关键监控指标：`completions/clipped_ratio`（源码 grpo_trainer.py L2306-2310，
= 回答最后一个 token 不是 EOS 的比例）。cap=128 时它高达 0.81：
被截断的回答长度挤在一起没有对比度、想教的"提前输出 EOS"行为恰好在数据里缺席。
cap_v2 还演示了"截断天花板"效应：曲线起点 109 远低于 R_new 的 175，
是被截断压下来的假象。

工程坑：三组同时启动会撞 torch 分布式默认端口 29500（EADDRINUSE），
单机多任务并行必须给每个进程独立的 `MASTER_PORT`。

### 七·补：reward 口径的最终归因 + cap_v3（300 步终点）

mean_length 在 cap=128 下是被审查（censored）的统计量——想写 175 token 的回答被砍到
128，曲线起点偏低是截断假象。跨 run 比较应该用 **reward**（所有组都是"离 20 字符
的距离"，同一货币）。各前 30 步 → 后 30 步的 reward 与斜率：

| 组 | 配置 | reward | 斜率（/步）|
|----|------|--------|-----------|
| R_old | 1e-6, 1.0, 128 | -9.93 → -9.21（300步）| 0.0024 |
| cap 组 | 1e-6, 1.0, 256 | -14.67 → -12.98 | 0.0113（cap 修复 ≈ ×4.7 @1e-6）|
| lr 组 | 1e-6, 0.7, 256 | -14.12 → -13.06 | 0.0071 |
| temp 组 | 2e-6, 1.0, 256 | -13.03 → -7.63 | 0.0360（lr 翻倍 ≈ ×3.2，同 1.0）|
| R_new | 2e-6, 0.7, 256 | -11.79 → -3.30（300步）| 0.028 |
| cap_v2/v3 | 2e-6, 0.7, 128 | -9.11 → -3.02（300步）| 0.018（cap=128 只慢 ~1.5x @2e-6）|

**cap_v3 终点**：reward -3.02 与 R_new 的 -3.30 打平；`clipped_ratio` 0.81 → **0.00**
——强驱动下模型把回答学到短于天花板，截断在后期自愈，cap=128 **没有终局 handicap**
（两次预测都低估了这一点：截断只伤害"长回答样本"，模型学会短回答后此类样本消失）。

**最终归因**：lr 翻倍 ≈ ×3~4（且决定有限步数预算内"能否看到收敛"——Adam 下总位移
= lr × 步数，exp1 信号丰富时这是唯一瓶颈）；cap 修复在弱 lr 下值 ×4.7、强 lr 下只值
×1.5（交互效应，强驱动可自愈）；温度 ≈ ×1（无显著影响）。
注意适用范围：lr 独大是 exp1 这类"信号丰富"任务的特征；exp2/exp3 的瓶颈在信号侧
（组内方差），那时组大小与奖励设计才是主角。

## 八、复现差异排查：作者模板验证实验（2026-10-02）

抓取作者原始脚本（[grpo-youtube-livestream-3-scripts](https://huggingface.co/sergiopaniego/grpo-youtube-livestream-3-scripts)
的 `train_grpo.py`）逐行 diff，发现三处差异：
1. **prompt 模板**（主嫌疑）：作者无专家前缀、测试包进代码围栏，且末尾有指令
   *"Write only the Python function, inside a ```python code block."*；我们无此约束，
   模型常写散文 → 合法 0 分多 → 基线低、信号噪
2. 代码提取：作者取最后一个代码块（`blocks[-1]`），我们拼接所有块
3. TRL 版本：作者锁 1.8.0，我们 1.10.0
（已排除：`test_setup_code` 仅 1/374 题非空；对话式与预渲染模板渲染等价）

重跑 exp2 k=2/k=8（`--prompt-style author --extract last_block`，
wandb：`exp2_mbpp_k2_author` / `exp2_mbpp_k8_author`）：

| run | 基线(first30) | 终点(last30) | 增益 | 对照 |
|-----|--------------|--------------|------|------|
| k8_author | **0.397** | **0.560** | +0.164 | 旧 k8：0.304→0.464（+0.160）|
| k2_author | **0.390** | 0.464 | **+0.074** | 旧 k2：0.328→0.362（+0.033）|

**结论**：
- 差异一**证实**：模板指令把基线拉回文章的 0.41 水平（+0.1 的整体位移）——
  "只写代码块"约束一个机制解释了起点差距
- 差异一**不解释增益差**：k8 增益 +0.164 与旧版持平（整条曲线上移而非变陡）；
  剩余差距（终点 0.56 vs 文章 0.67）的嫌疑收敛到 **TRL 1.8 vs 1.10 的实现差异**
  与文章曲线的测量口径/运行方差，留作已知限制
- 意外收获①：k2_author 增益翻倍（+0.033→+0.074）——强制纯代码输出让 2 样本
  小组的信号更干净，弱 baseline 场景反而受益更大
- 意外收获②：k8_author 全程仅 8 分钟（旧版 45 分钟）——纯代码回答又短又快，
  生成与判分同步提速
- 教训：复现文章时最大的隐形变量往往不是框架超参，而是 **prompt 措辞——它属于
  实验设计的一部分**；以及提取 grep 时警惕贪婪匹配（`.*` 会吞到行尾最后一个
  `/mean`，把重要性采样比当成奖励提取出来）

## 九、为什么 reward 平台到不了 1：逐题轨迹实测（2026-10-02）

问题：k8_author 的 reward 平台 ~0.56，为何不到 1？是训练数据不够吗？

方法：给奖励函数加逐题日志（`make_tests_reward_fn(log_file=...)`，每步把
(task_id, reward) 追加进 CSV，见 `--reward-log`），重跑 k8_author 300 步
（`exp2_mbpp_k8_author_logged`，7 分钟，4800 条记录，374 题全覆盖），逐题统计：

| 区域 | 题数 | 占比 | 机制 |
|------|------|------|------|
| 死区（历次 8 采样全 0）| 93 | **24.9%** | 全错组零方差 → 无梯度 → 训练无法改善 |
| 已掌握（历次全 1）| 58 | 15.5% | 全对组同样零方差，不再贡献改进 |
| 学习区（有对有错）| 223 | **59.6%** | 唯一有梯度地带，全部增益来自这里 |
| 解锁（先全 0 后 >0）| 14 | 3.7% | 死区靠采样运气逃逸的比例 |

**结论**：
- 若死区题不可解，reward 上限 ≈ 1 − 24.9% = **0.75**；扣除学习区未饱和与
  采样随机性（temp 0.7 下会做的题也非每份都对），实测 0.56 完全自洽
- **平台是结构性的，不是数据量问题**：死区题被多次访问但解锁率仅 3.7%——
  "全错 → 零方差 → 无梯度 → 无法改进"是 GRPO 的机制性锁死；加步数只能
  继续饱和学习区（外推 ~0.65+），消不掉死区
- 消掉死区的三条路（超出复现范畴）：更强基座模型 / 课程学习 / 加大探索
- 分析脚本：`scripts/analyze_rewards.py`；日志：`outputs/exp2_k8_rewards.csv`

## 十、方案1（阶梯奖励）验证：中性结果，假设证伪（2026-10-02）

按用户提议实现方案1（`--reward-style staged`：解析失败0 / 全崩0.1 / 跑通但全错0.2 /
部分通过 P/n / 全对 1.0），跑 `exp2_mbpp_k8_staged_v2`（author 模板+last_block，
其余同 k8_author；300 步 9 分钟）。CSV 双列记录（阶梯分, 真实通过率）。

| 指标（真实通过率口径）| k8_author | k8_staged_v2 |
|----------------------|-----------|--------------|
| 基线 / 终点 | 0.397 / 0.560 | 0.379 / 0.533 |
| 增益 | +0.164 | +0.154（持平）|
| 死区占比 | 24.9% | 24.6%（未破解）|
| 解锁题 | 3.7% | 2.4% |

**方案1 中性，假设证伪。** 阶梯分口径下"死区 0 题"是白送分数的幻觉；真实死区

阶梯没有制造方差；且它教的"别崩溃"是模型在 author 模板下已具备的技能，
不在通往"答案正确"的关键路径上。部分 credit 有效的前提——中间档位被异质占据
且因果在径——必须实测，不能想当然。

**后续方向**：方案4（测试增强：3→8~10 条 assert，细化学习区 59.6% 题的奖励
颗粒度，工程量大但打在最痛处）＞方案6（前沿采样：用逐题 CSV 把每步 prompt
名额花在学习区题上，避免 ~40% 步数浪费在零梯度题）＞接受 0.6B+300 步的平台。

## 十一、exp3 忠实复现：零结果与"飞轮启动失败"（2026-10-02）

重读原文并抓取作者 `train_grpo_pathological.py` 原脚本后，**纠正一个关键误译**：
原文"将奖励上限设置为 1"指归一化后的奖励天花板为 1.0，作者真实公式是
`min(len(blocks), 4) / 4`——四级跑道（1/2/3/4 块 = 0.25/0.5/0.75/1.0）。
此前两版实现（min(块数,1) 与 无上限）都不是作者的设计：
- "capped" 版把上限误读为"最多 1 块" → 第 1 步饱和冻结
- "uncapped" 版无分级归一化 → 漂到 2 块平衡点后冻结

## 十三、实验四：RLCD 方案B落地（2026-10-04，跨会话配方实证）

来自另一学习会话（Jev/RLCD）的配方：r = w₁·r_correct + w₂·r_cal，
其中 r_cal = 1-Brier（proper scoring rule 逼出校准）。方案B = 不改 trainer，
r_cal 按采样动作计分（弱信号版）。

**落地**：数据用本地缓存的 SetFit/sst5（影评情感 5 分类，候选=5 类别，
gold=标签）；prompt 停在 "Answer:"，completion 为单 token 编号；
`exp4_rlcd_grpo.py`（G=16, temp 1.0, 300 步，全程仅 2 分钟——生成只要 5 token）。

**结果**（`exp4_rlcd_G16_v2`）：
- accuracy：0.356 → 中段 0.463（+0.26 vs 随机 0.20）→ 尾部回落 0.36
- 零方差组 33~45%（5 选 1 组内多样性高，远好于 exp2 的 75%）
- 有梯度步 61%；completion 稳定 4-5 token（单 token 决策形态正确）

**结论**：
1. 配方核心预言应验——GRPO 能学分类决策，管线（数据/单token生成/判分/加权奖励）
   全部打通，基础设施复用率 ~70%
2. 方案B 的"信号弱"缺陷如约显现：r_cal 与 r_correct 同信号（单 token 拿不到
   分布 p），尾部无锚震荡——**校准必须走方案A**（Brier 进 loss）
3. 分类任务 0.4 秒/步，是方案A 的理想实验场

**方案A 待做**：subclass GRPOTrainer 覆写 compute_loss（L3061），加 λ·Brier
辅助损失（候选 logits → softmax → 与 one-hot gold 的多类 Brier），GRPO reward
只留 r_correct；验证指标 accuracy + ECE（torchmetrics.CalibrationError）。
